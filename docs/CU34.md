# CU34 — catálogo global de planes

Implementación mensual BOB, sin CU31/CU35/CU36. No hay precios ni planes de producción precargados. Se reutilizan autenticación JWT, identidad BIGINT, sesión síncrona y auditoría existentes. La web está en `/admin/planes` dentro del panel administrativo; el paquete lógico sigue siendo `auth/planes`.

## Funcionalidad y archivos

- `app/modules/auth/models.py`: definición única de Plan/VersionPlan, compartidos al igual que Clinica, Usuario y Rol. Importados directamente por Alembic y por el servicio del catálogo.
- `app/modules/auth/planes/`: esquemas, autorización global estricta, servicio transaccional y router `/api/v1/planes`, siguiendo la separación específica de `auth/clinicas`. Creación atómica, búsqueda/filtros/paginación, detalle, versiones, historial y desactivación idempotente. El archivo central de modelos no importa servicios ni routers.
- `alembic/versions/016_catalogo_planes_cu34.py`: revisión `cu34_catalogo_016`, padre `cu17_backup_merge_015`; tablas `planes`, `versiones_plan`, unicidad, restricciones, trigger de inmutabilidad y auditoría global limitada por CHECK.
- `alembic/env.py`, `app/main.py`: registro de modelos/router y manejador de errores.
- `app/core/audit.py`, `app/modules/auth/models.py`: auditoría sin clínica exclusivamente para catálogo; mapeo nullable de `Usuario.id_clinica` alineado con la migración 001 existente. No cambia la autenticación ni los IDs.
- `tests/cu34/`: permisos, validación, transacciones, historial, concurrencia y migración PostgreSQL.
- `scripts/cu34_local.py`, `scripts/cu34_web_check.py`: ejecución explícita aislada y recorrido web real.
- Frontend: tipos compartidos en `src/app/core/models/plan.models.ts` y cliente HTTP singleton en `src/app/core/services/planes.service.ts`, siguiendo `tenant.models.ts`/`ClinicasService`. Pantalla y pruebas en `src/app/features/auth/planes/planes-page.{ts,html,css,spec.ts}`; enlace en `admin-layout.html` y ruta protegida en `app.routes.ts`.
- SDD: `AGENTS.md`, `openspec/contracts/planes.md`, `openspec/specs/subscription-plan-catalog/spec.md`, cambio `openspec/changes/cu34-catalogo-planes/`. `SI2-Grupo3.md` conserva íntegramente el cambio del usuario.

## Ejecución local aislada (PowerShell)

Requisitos: Python 3.11+, Node compatible con el proyecto y PostgreSQL local. Los comandos siguientes se ejecutan desde `backend_Telemedicina`. No usar las credenciales del `.env`. El runner rechaza hosts remotos y nombres sin prefijo `cu34_local_` o `cu34_test_`. No importa `app.main`, no inicia backups ni otros procesos automáticos, y no crea tablas ni datos al arrancar el servidor.

```powershell
python -m venv .venv-cu34
.\.venv-cu34\Scripts\python.exe -m pip install -r requirements.txt
# En un servidor PostgreSQL LOCAL, usando una cuenta exclusiva de desarrollo:
createdb -h 127.0.0.1 -p 55434 -U cu34 cu34_test_catalog
$env:CU34_LOCAL_DATABASE_URL='postgresql+psycopg2://cu34@127.0.0.1:55434/cu34_test_catalog'
.\.venv-cu34\Scripts\python.exe -m scripts.cu34_local init
.\.venv-cu34\Scripts\python.exe -m scripts.cu34_local serve
```

`init` es una acción explícita: aplica Alembic y crea exclusivamente el usuario local `cu34-local@example.com`. Para una cuenta nueva solicita una contraseña mediante entrada oculta (mínimo ocho caracteres); si ya existe, conserva su contraseña. No crea planes ni imprime contraseñas. El runner genera claves JWT aleatorias en memoria al arrancar, por lo que reiniciarlo invalida sus tokens locales anteriores. Si el servidor local requiere contraseña, incluir únicamente la contraseña local en la URL.

Para crear un clúster nuevo en Windows, sustituir las rutas si se usa otra versión. La carpeta debe ser nueva y estar dentro del directorio temporal del proyecto:

```powershell
$pgBin='C:\Program Files\PostgreSQL\17\bin'
$cu34Data=Join-Path (Get-Location) 'tmp\cu34-pg'
& "$pgBin\initdb.exe" -D $cu34Data -U cu34 --auth=trust --encoding=UTF8 --locale=C
& "$pgBin\pg_ctl.exe" -D $cu34Data -l (Join-Path (Get-Location) 'tmp\cu34-pg.log') -o '-p 55434 -h 127.0.0.1' -w start
& "$pgBin\createdb.exe" -h 127.0.0.1 -p 55434 -U cu34 cu34_test_catalog
# Al terminar, detener SOLO ese clúster:
& "$pgBin\pg_ctl.exe" -D $cu34Data -m fast -w stop
```

La autenticación trust de este ejemplo solo es para el clúster efímero enlazado a `127.0.0.1`. No reemplazar la configuración de un servidor existente. Omitir el `createdb` duplicado si ya se creó la base.

En otra terminal, desde `frontend_Telemedicina`:

```powershell
npm ci
npm start -- --host 127.0.0.1 --port 4200
```

Abrir `http://localhost:4200/admin/planes`, iniciar sesión con el usuario local y crear los planes de prueba. La configuración de desarrollo existente apunta a `http://localhost:8000`. El harness sirve autenticación/contexto/catalogo; enlaces de módulos ajenos y la consulta opcional `/medicos/me` no forman parte del harness.

## Aplicación futura de la migración

No se ejecutó nada contra Neon. La revisión se comprobó en PostgreSQL 17 local, incluida la cadena completa desde una base vacía. Antes de desplegar, verificar respaldo, revisión actual y compatibilidad del esquema en el entorno de destino; usar las credenciales de despliegue mediante el mecanismo habitual. Ejecutar `alembic current` y `alembic heads`. Si la base está en `cu17_backup_merge_015`, ejecutar `alembic upgrade cu34_catalogo_016`, comprobar `alembic current` y realizar una prueba de lectura del catálogo. Desplegar API y web coordinadamente después de la migración. No usar `stamp` para omitir DDL ni `create_all` para sustituirla.

El downgrade vacío funciona. Con versiones o auditorías globales, se rechaza para no perder el historial: requiere un plan explícito de preservación de datos, no una reversión automática destructiva. No se modificaron migraciones anteriores.

## Contrato para los siguientes casos

`Plan.id/codigo` identifican la oferta; `VersionPlan.id` identifica las condiciones contratadas. `Plan.version_actual` es el contador del catálogo, no una referencia que deba resolverse en cada consulta de una suscripción. Condiciones monetarias como texto decimal BOB; ciclo MENSUAL; límites enteros o NULL; tarifas por recurso/unidad; servicios SaaS con códigos estables; demora en días calendario.

- CU31 deberá guardar el `version_id` elegido con precio/ciclo/moneda y comprobar que el plan admite nuevas contrataciones. Precio cero es gratuito; CU34 no inicia pagos.
- CU35 deberá consultar versiones de origen/destino y validar el estado antes de crear sus propias solicitudes. Ajustes, cancelación y programación quedan fuera de CU34.
- CU36 deberá usar límites/tarifas de la versión contratada y definir sus propias mediciones/liquidación. Una tarifa ausente no autoriza excedentes y NULL no tiene tarifa.

Todos los endpoints administrativos actuales son exclusivos del superadministrador. Los casos futuros deben reutilizar modelos/servicios con sus permisos de entidad o consultas internas; no abrir el CRUD global a administradores de clínicas. La futura suscripción deberá referenciar `versiones_plan.id` con integridad referencial, sin borrar versiones. No se comprobó conservación de suscripciones reales porque CU31 todavía no existe; sí se comprobó conservación exacta del historial del catálogo.
